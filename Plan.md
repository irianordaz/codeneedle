# Plan: `benchmark_suite.py` — LMStudio Model Benchmark Orchestrator

## Goal

Create `benchmark_suite.py` — a standalone Python script that discovers all models loaded in LMStudio via `lms ls`, creates per-model config files, runs benchmarks sequentially with 30-second pauses, and produces a Markdown results table.

## Requirements (from Prompt.md)

1. Discover all LMStudio models via `lms ls`
2. Use templates from `configs/models/` to find the best starting point per model
3. Create config files in `configs/models/user/` (create if not exists)
4. Name each model config: `{model}-{framework} where `{framework}` is `gguf` or `mlx`
6. Run each benchmark with `pixi run python bench.py run --corpus {code} --model {model}`
7. Sleep 30 seconds between benchmarks
8. Run `pixi run python analysis/visualize.py` at the end
9. Allow custom corpora path (default: `configs/corpora`)
10. Allow custom user-configs path (default: `configs/models/user` — matching line 4)
11. Execute all Python via `pixi run python`
12. Produce a Markdown table: rows = models, columns = pass, hallucinations, bonus, total runtime
13. Test with a small model like `mlx-community/qwen3.6-35b-a3b`

## File Structure

```
benchmark_suite.py          # New file — the orchestrator
configs/models/user/        # Created on first run — per-model TOMLs
```

## Implementation Steps

### Step 1: Parse CLI arguments

Use `argparse` with these options:

| Flag | Type | Default | Description |
|---|---|---|---|
| `--corpus` | `str` | *(required)* | Path to a Python source file (or corpus config). Passed as `{code}` to `bench.py run`. |
| `--max-tokens` | `int` | `65000` | Max tokens applied to all user configs and CLI overrides. |
| `--corpora-dir` | `Path` | `Path("configs/corpora")` | Directory containing corpus TOMLs (for finding corpora by name). |
| `--user-models-dir` | `Path` | `Path("configs/models/user")` | Directory to write user model TOMLs. |
| `--template-dir` | `Path` | `Path("configs/models")` | Directory containing template TOMLs to copy/modify. |
| `--dry-run` | `flag` | `False` | Print what would happen without executing benchmarks. |
| `--save-table` | `Path` | `None` | Path to write the Markdown results table (default: `results_table.md` in current dir). |

### Step 2: Discover models via `lms ls`

Run `lms ls` via `subprocess.run()` and parse its output to get a list of model identifiers. Each line corresponds to a model name usable with `bench.py run --model {name}`.

### Step 3: For each model, create a user config TOML

For each model discovered:

1. **Determine framework**: Check if the model name contains `mlx` (case-insensitive). If yes → `mlx`, otherwise → `gguf`.
2. **Build the config filename**: `{model}-{framework}-{max_tokens}.toml` (sanitize model name: replace `/` with `_`, remove special chars).
3. **Find the best template**: Search `--template-dir` for the closest matching template by comparing the model name stem (e.g., `qwen3.6:35b-a3b` matches `qwen3.6:35b-a3b-lms-gguf-65K.toml`).
   - Strategy: extract the model's core name (strip `-lms-*` suffix), then find the template whose stem shares the longest prefix match.
   - Among ties, prefer `gguf` over `mlx`, and larger `max_tokens` (e.g., `128K` over `65K`) if the model is known to need long context.
4. **Copy the template**: Read the template TOML, update the `max_tokens` field to the user-specified value, write to `{user-models-dir}/{model}-{framework}-{max_tokens}.toml`.
5. **Update the `name` field**: Keep the original `name` from the template (this is what LM Studio's server knows the model by).

TOML editing approach: Read as text, use regex to update the `max_tokens` line. Since existing configs are simple flat TOML, string replacement is sufficient.

### Step 4: Run benchmarks sequentially

For each user config TOML in `--user-models-dir`:

1. Extract the model name from the TOML (the `name` field).
2. Call: `pixi run python bench.py run --corpus {corpus} --model {config_path}`
   - `{config_path}` is the full path to the user TOML file (bench.py resolves it as a file path).
3. **Track runtime**: Record start and end time for each benchmark to calculate total runtime.
4. **Sleep 30 seconds** between benchmarks (`time.sleep(30)`).
5. Collect the exit code, stdout/stderr, and runtime from each run.

### Step 5: Parse benchmark results and generate Markdown table

After all benchmarks complete:

1. Read each `results/<corpus>__<model-stem>.json` file generated by the runs.
2. For each result, extract aggregated stats:
   - `passed`: count of functions that passed (primary_matched >= 8)
   - `hallucinated`: total hallucinated lines across all functions
   - `bonus`: total bonus matched lines across all functions
   - `runtime`: total runtime in seconds (start to end of the benchmark)
3. Write a Markdown table to `--save-table` (or `results_table.md` by default):

```markdown
| Model | Pass | Hallucinations | Bonus | Runtime (s) |
|---|---|---|---|---|
| qwen3.6:35b-a3b-gguf-65000 | 16 | 5 | 98 | 45.2 |
| gemma4:26b-gguf-65000 | 10 | 12 | 45 | 38.7 |
| ... | ... | ... | ... | ... |
```

Sort by pass count descending, then hallucinations ascending.

### Step 6: Run visualization

After all benchmarks and table generation, execute:

```
pixi run python analysis/visualize.py
```

Print a message indicating where the HTML dashboards were written.

## Edge Cases & Error Handling

- **`lms ls` returns nothing**: Exit with a clear error suggesting the user load a model in LM Studio first.
- **No templates found for a model**: Generate a minimal TOML with defaults (`base_url=http://localhost:1234`, `temperature=0.0`, `max_tokens=<value>`, `suppress_thinking=true`).
- **A single benchmark fails**: Log the error, continue with remaining models. Track failed models in the results table.
- **Corpus not found**: Exit with a clear error suggesting a valid corpus path.
- **`pixi` not found**: Exit with a clear error suggesting installation.

## Usage Examples

```bash
# Benchmark all LMStudio models against a corpus
pixi run python benchmark_suite.py --corpus jquery

# Custom corpora path, custom user-configs path, 128K max tokens
pixi run python benchmark_suite.py \
    --corpus jquery \
    --corpora-dir /path/to/corpora \
    --user-models-dir /path/to/user-configs \
    --max-tokens 128000

# Dry run: see what would be created and run
pixi run python benchmark_suite.py --corpus http_server --dry-run

# Save results table to a specific file
pixi run python benchmark_suite.py --corpus jquery --save-table my_results.md
```

## Review

Reviewed `benchmark_suite.py` against this plan and the surrounding code (`bench.py`, `bench/config.py`, the existing `configs/models/user/*.toml`, and `results_table.md`). The orchestration scaffolding works, but the table is currently meaningless — `results_table.md` shows two rows of all zeros tagged `(ERROR: exit code 1)` even though the corresponding JSON dumps in `results/` contain successful, fully-scored runs. The bugs below explain that and a few other things that will bite later.

### Critical bugs

1. **`bench.py run` exit code 1 is misinterpreted as a benchmark failure.**
   `bench.py` (`cmd_run`, line 167) returns `0 if passed == len(scores) else 1` — i.e. it exits 1 whenever *any* function falls short, not when the run itself crashed. `benchmark_suite.py:456-472` treats that as `error="exit code 1"` and forces `passed/hallucinated/bonus = 0`, which is then what gets written to the table. This is the single biggest reason `results_table.md` is empty. Either invoke `bench.py` differently (a flag that only exits non-zero on a real failure), or ignore exit code 1 from `bench.py` and rely solely on the JSON dump for pass/fail signal.

2. **Result-merge keys never match, so JSON stats are never merged into the table.**
   `parse_results_from_files` keys parsed results by the JSON filename stem before `__` — i.e. the *model config stem* like `mlx_community_qwen3_6_35b_a3b-mlx-65K`. `benchmark_results` keys are taken from the TOML's `name` field (e.g. `qwen3.6-35b-a3b`). The dict lookup at `benchmark_suite.py:679` never hits, so even if bug #1 were fixed the table would still show zeros. Fix: key both sides on the *config path stem* (which is what `bench/config.py:auto_dump_path` actually uses to name dumps), not on the TOML `name` field.

3. **The TOML `name` field is never updated to the discovered LMStudio model id.**
   `generate_user_configs` copies the matched template verbatim (only `max_tokens` is rewritten). Templates ship with a generic `name = "qwen3.6-35b-a3b"`, so both `mlx_community_qwen3_6_35b_a3b-mlx-65K.toml` and `qwen_qwen3_6_35b_a3b-gguf-65K.toml` end up pointing the OpenAI client at the *same* loaded model — the framework distinction is lost at the wire level. The user config's `name` must be rewritten to the model identifier returned by `lms ls` (e.g. `mlx-community/qwen3.6-35b-a3b`). Without this, "benchmarking MLX vs GGUF" silently benchmarks whichever variant LM Studio happened to load under that name, twice.

4. **`create_minimal_toml` writes invalid TOML.**
   `benchmark_suite.py:180` emits `max_tokens = {formatted}` where `formatted` is `"65K"`. `tomllib` will reject that as an unquoted bare key. Should be the integer (`max_tokens = {max_tokens}`). This path is dormant when templates exist, but it's a tripwire.

5. **`update_max_tokens_in_toml` silently no-ops when the template lacks a `max_tokens` line.**
   It's pure regex substitution with no insertion fallback. If a future template omits `max_tokens` (or comments it out), the user config inherits whatever `bench/config.py` defaults (6000), not `--max-tokens`. Either insert when missing, or parse → mutate → re-emit with `tomli_w`.

### Plan/implementation gaps

- **Tie-breaker direction is inverted.** Plan §Step 3 says "prefer `gguf` over `mlx`". The code's docstring (`find_best_template`, line 75) says "prefer `mlx`". Neither preference is actually implemented — the ranking only considers prefix-match and longest-common-substring. Pick a rule and enforce it explicitly (the cleanest fix: build a `(is_exact, is_prefix, lcs_len, framework_match)` tuple and `max()` over it).
- **`-lms-*` stripping is dead code.** Line 78 strips a suffix that current `lms ls` output doesn't produce. Harmless, but it advertises a behavior the script no longer needs.
- **MLX detection is redundant.** Line 62: `"-mlx-" in name.lower() or "mlx" in name.lower()` — the second clause subsumes the first. Drop the first.
- **Corpus validation is missing.** Plan promises "Corpus not found: exit with a clear error". Implementation just hands the string to `bench.py` and lets it fail there.
- **No flag for the 30s pause.** Plan and implementation both hardcode it. A `--cooldown-seconds` flag costs nothing and helps when iterating.
- **Step counter in `main()` is off-by-one.** Headings say "[1/5]" through "[5/5]" but visualization is a real sixth step. Either label it or relabel the rest.

### UX / operational issues

- **Subprocess output is captured, not streamed.** `run_subprocess` always `capture_output=True`. A 30-minute benchmark looks frozen with no progress. Stream stdout/stderr live for `bench.py` runs (capture only what you need for the error message), or at least surface a heartbeat.
- **No subprocess timeout.** A hung model means the entire orchestrator hangs forever. `subprocess.run(..., timeout=...)` with a generous ceiling (e.g. `model.timeout * 1.5 * k`) is cheap insurance.
- **`--dry-run` still sleeps 30s between iterations.** `benchmark_suite.py:431-433` sleeps even on the dry-run branch. Skip it.
- **No filter for "loaded vs installed" models.** `lms ls` lists every installed model, but only `✓ LOADED` ones can actually serve requests. Benchmarks against unloaded models will fail in the API call. Either parse the LOADED column and filter, or document that the user must pre-load.
- **Sanitization can collide.** `sanitize_model_name` collapses every non-alphanumeric to `_`, so `qwen/qwen3.6` and `qwen-qwen3.6` produce the same filename. Low probability, but worth either detecting or hashing on collision.
- **`generate_markdown_table` has no totals row and no source corpus column.** When you compare 10 models against 3 corpora over time, those columns matter. Cheap add.
- **`parse_lms_ls` summary-line filter is fragile.** The check on line 211 (`stripped.startswith("models, taking")`) only matches if "models, taking" is the start of a *line*, but the actual `lms ls` summary is one line: `"You have N models, taking X GiB"`. The `startswith("You have")` already catches it; the second branch is dead.

### Code quality (lower priority)

- `find_best_template` is unnecessarily tangled — the `is_better` branches re-derive the current best's prefix-match status instead of caching it. Replace with a single ranking tuple per candidate.
- `_longest_common_substring` allocates a full O(m·n) DP table for what could be two rolling rows. Negligible at these string sizes; flagging for hygiene.
- `import json` inside the loop in `parse_results_from_files` (line 531) — hoist to module level.
- The `except KeyError` on line 560 is dead code; the function only uses `.get()`.
- `--corpus` help text says "Path to a Python source file (or corpus config)" but `run_benchmarks` actually branches on `is_file()` and switches between `--file` and `--corpus` flags. Either rename the orchestrator's flag or document the dispatch.
- `discover_models` calls `sys.exit` directly. Fine for a script, awkward for testing — consider raising and catching in `main()`.
